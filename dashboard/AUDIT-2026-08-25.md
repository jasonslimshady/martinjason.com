# PART 1 — Speed & page-speed analysis

## 1.1 The payload, measured

Measured from the files as they ship today:

| Asset | Raw | gzip | Notes |
|---|---:|---:|---|
| `index.html` (total) | **549,745 B** | **136,282 B** | one file, everything inline |
| → inline `<style>` | 54,162 B | 11,836 B | lines 24–647 |
| → static body HTML | 70,484 B | 12,827 B | ~1,060 elements, all 9 panels always in the DOM |
| → inline `<script>` | **423,618 B** | **112,027 B** | lines 1750–9690, ~7,944 lines, **unminified** |
| `config.js` | 17,755 B | 7,069 B | 60% of it is `CONTRACT_TEMPLATE_HTML` (10,705 B) |
| `supabase-js@2.45.4` UMD (CDN) | ~120 KB | ~35 KB | *approximate — CDN unreachable from here* |
| Inter font (Google Fonts, 4 weights) | — | — | non-blocking (`media="print"` swap trick) |
| GSI client (`accounts.google.com`) | — | — | `async`, at end of body |

**Key numbers:** ~570 KB of first-party payload, of which **423 KB is unminified JavaScript that must be parsed and compiled before the app does anything**. Roughly 43 KB of that is comments and 24 KB is leading indentation.

## 1.2 The boot waterfall — why it feels slow before anything appears

Everything in the body is `hidden` until JS runs (`#screen-login`, `#screen-app` … all start `hidden`). So the only thing painted before the script executes is the `#loading` spinner. The real "app is usable" moment sits at the end of this chain:

```
1  HTML download            570 KB, single file — no streaming benefit, nothing usable mid-download
2  config.js                blocking classic script
3  supabase-js from CDN     BLOCKING cross-origin script — full DNS+TLS+download RTT to jsdelivr
4  parse/compile 423 KB JS  main thread, unminified
5  boot() → sb.auth.getSession()      ← network RTT to Supabase (token refresh if expired)
6  showApp() → await loadProjects()   ← SECOND serial network RTT, blocks everything after it
7  then, in parallel: loadStats (4 queries), loadCRM, loadPostCategories,
   loadLinkedInPosts, liCheckConnection (serverless), realtime WS
8  requestIdleCallback: loadQuotes, loadContracts, gaAutoInit
9  gaAutoInit → /api/ga-token (serverless cold start)
             → Google OAuth token endpoint
             → 5 sequential-after-token GA4 Data API calls
```

Steps 3, 5 and 6 are **three serial round-trips** that gate first useful paint. Step 6 is the cheapest to remove: `loadProjects()` is `await`ed purely so the two project dropdowns are populated — nothing on the first screen needs it.

**~11 Supabase REST calls + 2 serverless invocations + 5 GA4 calls fire on every single page load**, before you've clicked anything.

## 1.3 Geography — the multiplier on every one of those round-trips

| Component | Region |
|---|---|
| Supabase project `blibykmyvkdtdvgzuwyr` | **eu-west-1 (Ireland)** |
| Vercel functions | **iad1 (Washington DC)** — default; `vercel.json` sets no `regions` |
| Dashboard's own timezone constant | `Asia/Singapore` (`TZ`, line 9635) — i.e. you |

So a call to `/api/ga-token` goes **Asia → US-East → Ireland → US-East → Asia**. Realistically 600–900 ms before Google is even contacted. Direct Supabase REST calls from the browser are Asia → Ireland, ~180–250 ms each.

This is the single biggest structural cost and it's invisible in the code. Two levers: pin Vercel functions to a region near Supabase (`"regions": ["dub1"]` or `["fra1"]` in `vercel.json`) to kill the transatlantic hop, and/or reduce the *number* of round-trips (§1.6).

## 1.4 The image problem — the "low-quality previews" optimisation is inoperative

Commit `8336dcb` ("low-quality post previews in the feed, full quality on edit") implemented feed previews via Supabase Storage image transformations:

```js
const LI_IMG_TX = { width: 820, quality: 60, resize: 'contain' };   // index.html:8355
```

**Supabase image transformations require the Pro plan. This org is on the free plan (verified).** So `liProbeTransform()` fails, `liTransformMode` is set to `false`, and — because the result is cached in `localStorage` under `jm_img_tx` — it is `false` **permanently**, on every browser, forever. The feed serves full-resolution originals.

What that means in bytes (measured from `storage.objects`):

| | |
|---|---|
| Objects in `post-media` | 29 |
| Total | **23 MB** |
| Average object | **816 KB** |
| Largest object | **2,243 KB** |
| Media items referenced by current posts | 13 (across 9 of 30 posts) |

`loading="lazy"` limits this to what's actually scrolled into view, but scrolling the LinkedIn feed still pulls multi-megabyte JPEGs one card at a time — and the calendar tile grid renders 64px thumbnails from the *same* 800 KB–2 MB originals.

**This is the highest-value performance fix available.** Options, cheapest first:
1. Downscale/re-encode **at upload time** in the browser (canvas → WebP ~1200px, quality ~0.72) and store both the original and a `preview_path`. No plan change, no ongoing cost.
2. Upgrade Supabase to Pro so the existing transformation code starts working. Also requires clearing the sticky `jm_img_tx` cache (see P2-6).

## 1.5 Per-panel cost

| Panel | Network on open | Cached? |
|---|---|---|
| **Analytics** (default panel) | `/api/ga-token` (serverless, cold-start) → Google token → **5 GA4 Data API calls** | **No cache at all** — full refetch on every load and every range change |
| **SEO** | **10 Search Console queries in parallel**, one with `rowLimit: 5000` | No cache; refetched on every range/property change |
| **LinkedIn** | 1 posts query + **up to 13 individual `createSignedUrl` calls** (one per media item) | posts cached; signed URLs not |
| **Klaviyo** | 1 `/api/klaviyo` call which fans out to ~5 Klaviyo API calls server-side | No cache |
| **Rechnungen** | invoices + reminders | No cache |
| Kunden (CRM) | clients | **Cached** (localStorage SWR) |

Only **two** datasets use the stale-while-revalidate cache the file's own header comment describes:

```
grep "cacheGet('|cacheSet('" → clients (2051, 2057), posts (8414, 8420)
```

Invoices, quotes, contracts, projects, time entries, stats, GA, SEO and Klaviyo all refetch from zero. That's the largest gap between the intended design and the actual code.

Also: `liResolveMediaUrls()` issues N separate `createSignedUrl()` calls in a `Promise.all`. Supabase has a batch `createSignedUrls()` (plural) that does the whole set in one request — 13 requests → 1.

## 1.6 Runtime / rendering

The CSS-level scroll work has already been done well and should not be touched (see Part 3). What's left:

- **GA Live mode polls forever.** `setInterval(renderLive, 30000)` (line 6446) fires **5 GA4 realtime API calls every 30 s**, indefinitely, and is not paused when the tab is backgrounded. `gaStopLive()` is called on panel switch, but a backgrounded tab left on Analytics keeps burning quota. Fix: gate on `document.visibilityState`.
- **Realtime double-refetch.** `subscribeLinkedInRealtime()` (line 8545) calls a full `loadLinkedInPosts()` on *any* `posts` change, and the mutation helpers (`changePostStatus`, etc.) already call it themselves — so one status change triggers two full `select('*')` refetches and two re-renders. Not debounced. (Currently moot — see P1-2, the subscription never actually fires.)
- **`JSON.stringify` diffing.** `loadLinkedInPosts()` stringifies the whole post array twice per load to decide whether to re-render. Fine at 30 posts, quadratic-feeling at 300.
- **`html2pdf` / `html2canvas` at `scale: 2`** rasterises an 820px document on the main thread — the UI freezes for the duration. On-demand only, so acceptable, but the ZIP export runs it once **per invoice in a serial loop** with no yielding.
- **`<video preload="metadata">`** on every video card in the feed triggers a metadata range-request per video.
- **No `preconnect` for `martinjason.com`**, which serves `LI_PROFILE_PIC` on every post card (line 8570).

## 1.7 Dead weight still shipping

- `.timer-blobs` / `.timer-blob--a|b|c` — full CSS blocks (lines 286–294) plus a `@keyframes timer-drift` animation and 4 DOM elements (lines 814–818), all killed by `display:none!important` at line 153. Delete the CSS, the keyframes and the markup.
- `.bg-blobs` / `.bg-grain` / `.blob` — same story: markup at lines 652–658, disabled at line 70.
- `backdrop-filter` declarations on `.ga-range-btn`, `.ga-live-btn`, `.ga-connect-btn`, `.act-type-btn`, `.klv-range`, `.pto-btn`, `.pto-view-toggle`, `.timer-hero` (lines 204, 206, 220, 272, 568, 583, 602, 282) are all overridden to `none!important` at line 152. Dead declarations.
- `CONTRACT_TEMPLATE_HTML` — 10.7 KB of German contract boilerplate parsed on **every page load**, used only when you open the Vertrag builder. Move it to a separately fetched file.

## 1.8 Recommended optimisation order

Ranked by (impact ÷ effort). Estimates are reasoned from measured bytes and the round-trip structure, not from a live trace.

| # | Change | Effort | Expected effect |
|---|---|---|---|
| 1 | **Shrink feed images** (resize on upload, §1.4) | M | Removes megabytes per feed scroll. Biggest single win. |
| 2 | **Drop `await` on `loadProjects()`** in `showApp()` (line 1880); populate dropdowns when it resolves | XS | Removes one full serial RTT (~200 ms) from first paint |
| 3 | **`defer` the supabase-js CDN script**, or self-host it and bundle | XS | Removes a blocking cross-origin RTT |
| 4 | **Minify the inline JS** at build time (esbuild/terser) | S | 423 KB → ~180 KB raw; less download, much less parse/compile |
| 5 | **Pin Vercel functions to `dub1`/`fra1`** in `vercel.json` | XS | Kills the Asia→US→Ireland detour on all 5 API routes |
| 6 | **Extend the localStorage SWR cache** to invoices, quotes, contracts, projects, stats, GA and SEO | M | Every panel paints instantly on repeat visits; matches the design that's already documented in the file |
| 7 | **Batch signed URLs** — `createSignedUrls()` (plural) in `liResolveMediaUrls` | XS | 13 requests → 1 |
| 8 | **Gate GA Live polling on `visibilityState`** | XS | Stops background quota burn |
| 9 | **Split `index.html`** — extract `<style>` to a cached `.css` and the panel-specific JS into modules loaded per panel | L | Structural; makes everything above easier and caches properly across deploys |
| 10 | **Delete dead CSS/markup + move `CONTRACT_TEMPLATE_HTML` out of `config.js`** | XS | ~15 KB and a cleaner file |

Items 2, 3, 5, 7, 8 and 10 are all XS and together remove two serial round-trips, a transatlantic hop and a background poll. That's the cheap half of the win.

# PART 2 — Prioritised issues (security, bugs, broken functions)

## P0 — Fix first

### P0-1 · pdf.js 3.11.174 is vulnerable to CVE-2024-4367 (arbitrary JS execution from a crafted PDF)

**Where:** `index.html:1788` (`LIB_PDFJS`), `index.html:4118` (worker), used by `processScanFile()` at 4110.

```js
const LIB_PDFJS = 'https://cdnjs.cloudflare.com/ajax/libs/pdf.js/3.11.174/pdf.min.js';
```

pdf.js versions **before 4.2.67** allow a malicious PDF to execute arbitrary JavaScript in the page's origin (the font-handling `isEvalSupported` path). The "Rechnung hinzufügen" flow feeds arbitrary user-supplied PDFs straight into `pdfjsLib.getDocument()`. Because the dashboard has no CSP, that JS gets the full origin: the Supabase session in `localStorage`, the in-memory GA/Gmail tokens, and the ability to call `/api/*` as you.

Attack path is realistic: any PDF you drop in from a client or a supplier.

**Fix:** upgrade to pdf.js ≥ 4.2.67 (and match the `workerSrc` version), **or** as an immediate stopgap pass `{ data: buf, isEvalSupported: false }` to `getDocument()`.

### P0-2 · No Content-Security-Policy, and no SRI on any CDN script

**Where:** `dashboard/vercel.json` (headers block), `index.html:1749`, `1788–1790`, `4118`, `9693`.

Five third-party scripts are loaded with **no `integrity` attribute and no CSP** to constrain them:

| Script | Host |
|---|---|
| `supabase-js@2.45.4` | cdn.jsdelivr.net |
| `pdf.js` + worker | cdnjs.cloudflare.com |
| `jszip@3.10.1` | cdn.jsdelivr.net |
| `html2pdf.js@0.10.1` | cdn.jsdelivr.net |
| GSI client | accounts.google.com |

A compromise (or DNS/BGP hijack) of jsdelivr or cdnjs is a complete takeover of the dashboard: the Supabase session, every invoice, every client record, and the LinkedIn posting ability. `supabase-js` is the worst case — it's loaded on every page view and it *is* the auth layer.

`vercel.json` sets `X-Frame-Options`, `X-Content-Type-Options` and `Referrer-Policy`, which is a good start, but no `Content-Security-Policy`, no `Strict-Transport-Security`, no `Permissions-Policy`.

**Fix:** add `integrity` + `crossorigin="anonymous"` to all four pinned CDN scripts (or self-host them — better, and it also helps §1.2). Then add a CSP. Note the app uses inline `<script>`, inline `<style>`, inline `onclick=` handlers and `style="…"` attributes throughout, so a strict CSP needs either a nonce/hash pass or a staged rollout via `Content-Security-Policy-Report-Only` first. Add `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload` in the same pass.

> Do **not** add `Cross-Origin-Opener-Policy: same-origin` — it would break the LinkedIn OAuth popup's `postMessage` back to the opener (`linkedin-callback.html:21`).

### P0-3 · `/api/linkedin-cron` may be publicly triggerable — verify `CRON_SECRET` is set

**Where:** `api/linkedin-cron.js:43–47`.

```js
const cronSecret = process.env.CRON_SECRET;
if (cronSecret) {                                     // ← the whole check is optional
  const auth = req.headers.authorization || '';
  if (auth !== `Bearer ${cronSecret}`) return res.status(401).json({ error: 'Unauthorized' });
}
```

If `CRON_SECRET` is unset, **anyone who knows the URL can publish your scheduled LinkedIn posts on demand** — no auth of any kind. The endpoint also doesn't check the HTTP method, so a plain `GET` works.

I cannot read Vercel env values, so this needs manual confirmation. What the evidence shows: 60 invocations of `/api/linkedin-cron` in the last 24 h, **all HTTP 200, zero 4xx**. That's consistent with a correctly-configured external pinger *and* with no secret being required at all — it doesn't distinguish them.

**Fix:** confirm `CRON_SECRET` exists in Vercel → Project Settings → Environment Variables. If it doesn't, set one and add it to the external pinger's `Authorization` header. Then make the check mandatory — fail closed with a 500 if the env var is missing, rather than silently running unauthenticated. Also reject non-`POST` (or non-`GET`) methods explicitly.

## P1 — Broken / silently non-functional

### P1-1 · LinkedIn access token expires 2026-10-19 with no refresh token — auto-posting will stop dead

**Where:** live `app_tokens` row `id='linkedin'`; logic in `api/_lib/linkedin.js:65–99`.

Verified state of the stored token:

| Field | Value |
|---|---|
| `refresh_token` | **absent** |
| `expires_at` | **2026-10-19 06:33 UTC** |
| `person_urn` | present |

`ensureFreshToken()` handles this correctly — it throws `reauth_required`. But the consequence is that **on 2026-10-19 every scheduled post silently stops publishing**. The cron writes `last_publish_error` on each due post, leaves it as `status='approved'`, and nothing surfaces it: the dashboard renders `last_publish_error` nowhere, and there is no alert.

The connect flow already warns about this once, at connect time (`index.html:8938`), but that toast is long gone.

**Fix (two parts):**
1. Surface `last_publish_error` in the LinkedIn panel — a red badge on the row and a count in the sidebar. A post that failed to publish should be impossible to miss.
2. Add an expiry warning: `liCheckConnection()` already calls `/api/linkedin-token`, which returns `expires_in`. Show a persistent banner when it drops under ~14 days. Consider a scheduled reminder for 2026-10-05.

### P1-2 · LinkedIn realtime updates never fire — the `posts` table is not in the realtime publication

**Where:** `index.html:8545–8550`.

```js
liRealtimeSub = sb.channel('posts-changes')
  .on('postgres_changes', { event:'*', schema:'public', table:'posts' }, () => loadLinkedInPosts())
  .subscribe();
```

Verified on the live database:

```sql
select p.pubname, c.relname from pg_publication p
  left join pg_publication_rel pr on pr.prpubid = p.oid
  left join pg_class c on c.oid = pr.prrelid;
-- supabase_realtime                       → (no tables)
-- supabase_realtime_messages_publication  → messages
```

**The `supabase_realtime` publication contains no tables.** The subscription connects, holds a WebSocket open for the whole session, and receives nothing — ever. When the external content-engine automation inserts new drafts, the dashboard doesn't notice; you have to reload.

**Fix:** either `ALTER PUBLICATION supabase_realtime ADD TABLE posts;` (and add it to `supabase-setup.sql` so it survives a rebuild), or delete `subscribeLinkedInRealtime()` and stop paying for a WebSocket that does nothing. If you enable it, also debounce the handler — see §1.6.

### P1-3 · Feed images break after 1 hour on an open tab

**Where:** `index.html:8342` (`liMediaUrlCache`), `8392` (`createSignedUrl(path, 3600)`).

```js
let liMediaUrlCache = {};                                       // never invalidated
const sign = (path, opts) => sb.storage.from('post-media').createSignedUrl(path, 3600, opts)
…
if(!m.path || liMediaUrlCache[m.path]) return;                  // cached = permanently skipped
```

Signed URLs live 3600 s. The cache is in-memory with **no expiry and no invalidation**. Leave the dashboard open for over an hour — which is the normal way you use it — and every post image and calendar thumbnail turns into a broken image, until you reload.

**Fix:** store `{ url, expiresAt }` and treat an entry as a miss once it's within ~5 minutes of expiry. The guard at 8386 then re-signs it naturally.

### P1-4 · Company-page posting will fail for any post with media

**Where:** `api/_lib/linkedin.js:257–263`.

```js
const targets = [{ label: 'Profil', author: person_urn }];
if (LINKEDIN_ORG_ID) targets.push({ label: 'Unternehmensseite', author: `urn:li:organization:${LINKEDIN_ORG_ID}` });

const content = await buildContent(access_token, person_urn, serviceKey, post.media);
//                                              ^^^^^^^^^^ always the person URN
```

The media asset is uploaded **once**, owned by `person_urn`, and then the same asset URN is attached to both the profile post and the organisation post. LinkedIn requires the asset owner to match the post author — the organisation post will be rejected.

Dormant today (`LINKEDIN_ORGANIZATION_ID` appears unset, and the OAuth scope at `index.html:8863` is `openid profile w_member_social` with no `w_organization_social`), but it will bite the moment Community Management API approval comes through.

**Fix:** build content per target, uploading the asset with `t.author` as owner.

### P1-5 · Concurrent cron runs can double-publish a post

**Where:** `api/linkedin-cron.js:53–58`, `api/linkedin-publish.js:66–91`.

The cron selects `status=eq.approved`, publishes, *then* patches `status='posted'`. There's no claim/lock between select and patch. The file's own comment argues it's idempotent:

> *"this endpoint is idempotent (a post only publishes once, since it's no longer status='approved' after the first successful run)"*

That's only true if runs never overlap. Publishing with media takes seconds (download from Storage → upload to LinkedIn → build PDF for carousels). Two overlapping pings — or a ping racing your manual "Jetzt auf LinkedIn posten" click — both see `approved` and both publish. **The result is a duplicate post on your LinkedIn feed**, which is not recoverable from the dashboard.

Higher risk than it looks: the Vercel cron (`0 3 * * *`) and an external pinger both hit this endpoint, and there are ~60 invocations/day.

**Fix:** claim the row first — `PATCH … ?id=eq.X&status=eq.approved` with `{status:'publishing'}` and `Prefer: return=representation`; only proceed if a row comes back. Reset to `approved` on failure. Add `'publishing'` to the status maps so the UI renders it.

## P2 — Real bugs, user-visible

### P2-1 · Invoice numbers can carry the wrong date (timezone mismatch)

**Where:** `index.html:4896–4906` vs `4236` / `5567`.

```js
async function nextInvoiceNumber(excludeId){
  const d = new Date();                                    // ← BROWSER-local date
  const base = `INV-${pad(d.getDate())}-${pad(d.getMonth()+1)}-${d.getFullYear()}`;
```

but the invoice's actual date field uses the dashboard timezone:

```js
invoice_date: $('sc-date')?.value || today(),              // today() = Asia/Singapore
```

The whole app deliberately runs on `TZ = 'Asia/Singapore'` (line 9635, with a comment explaining exactly why). `nextInvoiceNumber` is the one place that didn't get the memo. Create an invoice from Europe after ~18:00 local and you get `INV-24-08-2026` stamped on a record whose `invoice_date` is `2026-08-25`. On a German invoice that's a genuine bookkeeping defect, not a cosmetic one.

Same bug, identical shape, in `nextQuoteNumber` (5382) and `nextContractNumber` (5850).

**Fix:** derive all three from `today()`.

### P2-2 · Calendar month navigation skips months on the 29th–31st

**Where:** `index.html:8487–8489`.

```js
$('li-grid-prev').addEventListener('click', ()=>{ liGridRefDate.setMonth(liGridRefDate.getMonth()-1); … });
```

`liGridRefDate` is a mutable shared `Date` initialised to `new Date()`. `setMonth()` overflows: on 31 May, `setMonth(3)` gives "31 April" → normalises to **1 May**. The label doesn't change and the month appears stuck. On 31 March, `setMonth(1)` → "31 February" → **3 March**. Same for `li-grid-next`.

Reproduces only on the 29th–31st, which is why it looks intermittent.

**Fix:** anchor to the 1st before shifting — `new Date(y, m + delta, 1)`.

### P2-3 · Category colours bypass `safeColor()` and are injected raw into `style` attributes

**Where:** `index.html:8216` and `8258`.

```js
// 8216
return `<span class="li-cat-tag" style="background:${c.color};color:${liCatContrast(c.color)}">…`;
// 8258
<summary class="li-cat-color-dot" style="background:${c.color}" title="Farbe ändern"></summary>
```

The codebase has a helper for exactly this, and uses it correctly elsewhere (line 3289):

```js
function safeColor(c){ return c && /^#[0-9A-Fa-f]{6}$/.test(c) ? c : null; }   // line 9645
```

`post_categories.color` currently only ever gets values from a fixed swatch list, so this isn't exploitable today — but it's an unescaped value in an HTML attribute, one direct DB write away from attribute-breakout XSS. It's an inconsistency in an otherwise careful escaping discipline (`esc()` is used 201 times).

**Fix:** route both through `safeColor()` with a fallback, same as line 3289.

### P2-4 · `last_publish_error` is written but never displayed

**Where:** written at `api/linkedin-cron.js:72, 112, 120`; **zero** references in `index.html`.

When an automatic publish fails, the cron records exactly why — and the dashboard shows nothing. The post just sits in "Freigegeben" looking normal. This is the mechanism that will make P1-1 invisible when the token expires.

**Fix:** render it on the post row (red badge + tooltip) and count failures into the sidebar badge.

### P2-5 · Overdue auto-flip is fire-and-forget and can silently diverge from the database

**Where:** `index.html:3436`.

```js
nowOverdue.forEach(i=>{ i.status='overdue'; });                         // UI updated immediately
sb.from('invoices').update({status:'overdue'}).in('id',…).then(()=>loadStats());   // no .catch()
```

The local objects are mutated first and the write is unawaited with no error handling. If it fails (offline, RLS hiccup, expired token), the table shows "Überfällig" while the database still says "sent" — and you'd only notice via a mail that never got chased.

**Fix:** await it, or add `.catch()` that reverts the local mutation and toasts.

### P2-6 · The image-transformation probe result is cached permanently, including its failures

**Where:** `index.html:8371–8379`.

```js
if(cached === '0'){ liTransformMode = false; return false; }   // never re-probed
```

One transient failure — offline, a slow response, a 5xx — locks the browser into "no transformations" **forever**. It also means that if you upgrade Supabase to Pro (see §1.4), every existing browser keeps serving full-resolution originals until someone manually clears `localStorage`.

**Fix:** store `{ value, checkedAt }` and re-probe negative results after ~24 h. Positive results can stay sticky.

### P2-7 · ZIP export revokes its blob URL before the download is guaranteed to start

**Where:** `index.html:3873–3876`.

```js
a.href = URL.createObjectURL(zipBlob);
document.body.appendChild(a); a.click(); a.remove();
URL.revokeObjectURL(a.href);            // ← synchronous, same tick as click()
```

Revoking in the same tick as `click()` is a known race; some browsers cancel the download. Chrome usually survives it, Firefox and Safari are less reliable.

**Fix:** `setTimeout(() => URL.revokeObjectURL(url), 60_000)`.

### P2-8 · Deleted posts, quotes and contracts leak their files in Storage forever

**Where:** `index.html:8809–8815` (`deletePostRow`). Only `invoice-pdfs` has a cleanup path (line 3985).


## P3 — Hardening and hygiene

### P3-1 · `dashboard.martinjason.com` is indexable

No `robots.txt` in `dashboard/` and no `noindex` meta in `index.html`. The root `robots.txt` lives on `martinjason.com` and does **not** apply to the subdomain — it's a separate Vercel project. **Fix:** add `dashboard/robots.txt` with `User-agent: * / Disallow: /` and `<meta name="robots" content="noindex,nofollow">`.

### P3-2 · Klaviyo date parameters are unvalidated and interpolated into Klaviyo's filter DSL

**Where:** `api/klaviyo.js:75, 83–84, 119–121, 176–177`.

```js
const { resource, start, end } = req.query;
const s = start || defaultStart;
…
filter: [`greater-or-equal(datetime,${s}T00:00:00+00:00)`, `less-than(datetime,${e}T23:59:59+00:00)`]
```

`start`/`end` reach an upstream query language with no shape check. Only the authenticated owner can call this endpoint, so the practical impact is self-injection — but it's unvalidated input in a query string and costs one regex to close.

**Fix:** reject anything not matching `/^\d{4}-\d{2}-\d{2}$/`.

### P3-3 · OAuth `state` uses `Math.random()`

**Where:** `index.html:8894`.

```js

```

Not cryptographically random. Mitigated in practice — the callback `postMessage`s to `window.location.origin` and the listener checks `e.origin` (8914) — but there's no reason not to use `crypto.randomUUID()`.

Same function: the `message` listener is never removed on the `popup.closed` rejection path (8913–8922), so every abandoned connect attempt leaks a listener for the life of the page.

### P3-4 · `handle_updated_at` has a mutable `search_path`

Flagged by the Supabase security advisor. A `SECURITY DEFINER`-adjacent function without a pinned `search_path` is a standard privilege-escalation shape.

**Fix:** `ALTER FUNCTION public.handle_updated_at() SET search_path = public, pg_temp;` — and mirror it in `supabase-setup.sql`.

### P3-6 · Gmail draft assembly is memory-heavy for large PDFs

**Where:** `index.html:9563, 9591`.

```js
const b64utf8 = s => btoa(unescape(encodeURIComponent(s)));
…
return b64utf8(msg).replace(/\+/g,'-')…                          // base64 of a string that already contains base64
```

The PDF is base64'd, embedded in a MIME string, then the whole string is base64'd again — roughly 1.8× the PDF size held three times over, all on the main thread. `unescape` is also deprecated. Gmail's simple-upload path caps at 5 MB; a multi-page invoice with a logo can approach it. Consider Gmail's multipart/resumable upload, or at least a size check with a clear error.

- **`ALLOWED_EMAIL` is correct.** `config.js:21` and all five API routes use `jasonmartinde@gmail.com`, which differs from the `jasonmartinph@gmail.com` in `INVOICE_FROM`.
